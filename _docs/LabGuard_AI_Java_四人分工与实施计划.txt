
LabGuard AI 四人分工与实施计划
Java 原型  |  2026 年 10 月 16 日至 10 月 21 日
本计划用于指导四人团队在六天内完成 LabGuard AI 可运行原型。实施重点是打通“上传实验室图片、真实视觉 AI 分析、人工确认、创建整改工单、提交整改、复查关闭或退回”的最小闭环，并保证结果真实、状态可追踪、数据可持久化、关键逻辑可测试。

一 项目范围与技术决策
技术决策：两份项目材料对实现技术栈的描述不一致，其中一份采用 Java，另一份仍保留 Python 和 Streamlit 方案。根据团队最新要求，本计划统一采用 Java 17 技术路线；业务目标、数据对象、安全边界和验收要求继续吸收两份材料中的有效内容。
当前项目目录状态：工作区中尚无 README、Java 源码、Maven 配置或测试，因此实施计划按从空工程启动安排。团队在开始编码前应先建立共享仓库、分支规则和接口契约，避免四人分别创建不兼容的工程骨架。
核心业务闭环
上传 JPG 或 PNG 实验室现场图片，并保存巡检基本信息。
调用真实多模态视觉 API，返回结构化的疑似风险线索。
展示风险类别、等级、位置、可见证据、置信度或不确定性以及整改建议。
由人工确认、修改或驳回模型结果；只有确认后的风险才可创建工单。
责任人提交整改说明和整改后照片，工单进入待复查。
复查通过后关闭工单；未通过则退回待整改并保留复查意见。
首版边界
AI 只判断图片中可见线索，不判断设备是否通电、设备内部状态或化学品真实成分。
模型结果是辅助建议，不替代实验室安全人员的专业判断。
首版不开发实时视频、多角色复杂权限、消息通知、模型训练、多智能体协作和复杂报表。
图片、API 密钥及其他敏感信息不得提交到公开仓库。

工单状态规则
待确认  →  待整改  →  待复查  →  已关闭
复查不通过：待复查  →  待整改
未人工确认的风险不能创建工单。
未提交整改说明和必要证据时，不能进入待复查。
只有待复查工单能够执行通过或退回；已关闭工单不能继续修改状态。
每次状态变化建议写入 AuditEvent，记录操作人、时间、前后状态和复查意见。

团队选定视觉 API 服务商后，必须依据其官方文档确认以下配置。未获得这些信息前，不应声称真实 API 已经接通。

real 模式缺少接口地址、密钥或模型时，停止调用并显示“视觉 API 未配置完整”。
API 调用失败时显示真实错误类别并允许重试或人工处理，不自动切换为伪造成功结果。
demo 模式只能返回明确标记为 DEMO 的固定样例，页面顶部和数据记录中均需显示“演示数据”。
AI 响应必须先经过 JSON 结构和字段类型校验，原始文本不能直接成为工单事实。

十 每日完成定义
一项任务只有同时满足以下条件，才可以标记为完成：
□ 代码已提交到个人功能分支，并通过代码格式和编译检查。
□ 新增或修改的核心逻辑已有对应测试，测试结果已记录。
□ 模块对外接口和配置变更已同步给受影响成员。
□ 功能在本地能够运行，不依赖未提交的个人文件或硬编码路径。
□ 错误路径已验证，尤其是 API 未配置、数据库失败、表单非法和状态非法。
□ 合并后主分支仍能启动，并且核心闭环未发生回归。
最终目标：到 2026 年 10 月 21 日晚上，团队交付的不是静态页面或伪造 AI 演示，而是一个能够真实调用视觉模型、保留人工确认、持久化工单并完成整改复查状态闭环的 Java 原型。
