
LabGuard AI 项目说明书
Java 技术方案｜实验室安全巡检智能体
项目名称：LabGuard AI（实验室安全巡检智能体）
项目类型：智能体应用 / 创新原型
主要开发语言：Java 17
一、项目背景
实验室日常运行涉及仪器设备、用电设施、实验通道及各类物品的规范管理。传统巡检通常依赖人工观察、纸面或表格记录以及线下通知，可能存在记录分散、隐患描述不统一、责任分配不及时、整改进度难以跟踪和复查结果不易追溯等问题。
随着多模态视觉模型和智能体应用的发展，可以将图像理解能力与结构化业务流程结合，辅助工作人员发现图片中可见的潜在安全隐患，并把识别结果转化为可追踪的整改工单。因此，本项目拟开发 LabGuard AI，将图片巡检、风险审核、整改任务管理和复查闭环整合为一个可运行的原型系统。
本项目定位为安全管理辅助工具。AI 输出仅用于提示和辅助判断，不能替代安全管理人员的现场检查、专业判断及既有安全制度。
二、应用场景
1. 实验室日常巡检
巡检人员上传实验室现场照片，系统对图像中可见的潜在问题进行辅助分析，并生成结构化的风险提示，便于统一记录。
2. 通道与消防通行区域检查
针对图片中疑似被物品阻挡的通道或出入口，系统提供风险提示和建议核查措施；最终是否构成隐患由人员现场确认。
3. 隐患整改任务分配
经人工确认的风险可转换为整改工单，记录风险类别、位置、建议措施和责任人，减少口头通知造成的信息遗漏。
4. 整改复查与闭环管理
责任人提交整改说明后，工单进入待复查状态。复查通过则关闭工单，未通过则退回整改，形成可追踪的处理过程。
5. 竞赛演示与原型验证
通过一套可本地运行的 Web 应用展示从图片上传到工单关闭的端到端流程，验证 AI 能力与实际业务流程的结合。
三、核心功能
1. 图片上传与巡检记录
支持用户通过网页上传常见格式的实验室图片，并记录文件名、巡检时间及分析模式，作为后续查询与演示的基础。
2. AI 辅助风险识别
通过适配多模态视觉 API，对图片中可见的潜在安全风险进行分析。输出结构化字段，包括风险类别、风险等级、位置描述、可见证据、置信度、建议措施及是否需要人工复核。
3. 人工确认与风险审核
识别结果展示后由用户确认，再决定是否创建整改工单。对不确定、遮挡或无法从图像中验证的事项，系统应明确提示人工现场核查。
4. 整改工单创建与责任分配
将确认后的风险转为工单，记录风险信息、责任人、当前状态、整改说明和复查意见，便于跟踪任务进度。
5. 整改提交与复查
责任人提交整改说明后，工单从待整改进入待复查。复查通过后关闭工单；复查未通过则返回待整改状态。
6. 数据持久化
使用 SQLite 保存工单和相关业务数据，应用重启后仍可保留已保存的记录，降低原型部署复杂度。
7. 异常处理与演示模式
在真实 AI API 未配置或调用失败时显示明确错误，不伪造 AI 成功结果。开发阶段可使用清楚标记的演示数据验证界面与工单流程。
四、创新点
1. 将视觉识别与整改工作流结合
项目不止于图片问答或风险描述，而是把 AI 分析结果接入人工审核、工单创建、责任分配、整改提交和复查关闭流程，使结果能够进入实际管理环节。
2. 人机协同的风险确认机制
AI 负责提供辅助线索，工作人员保留确认、分派和复查决策权，降低模型误判直接影响管理动作的风险。
3. 面向闭环的工单状态管理
通过明确的待整改、待复查、已关闭状态和复查失败回退机制，形成可展示、可测试、可追踪的业务闭环。
4. 结构化风险信息
将自然语言分析结果整理为类别、位置、证据、等级和建议措施等字段，便于后续查询、统计和系统扩展。
5. 轻量化部署与模块化设计
采用 Java、Spring Boot 和 SQLite 构建模块化应用，减少初期部署依赖，并将视觉 API、网页控制层和工单业务逻辑分离，方便团队并行开发。
五、技术方案
5.1 技术架构
系统采用分层结构：前端展示层负责图片上传、风险结果展示及工单操作；控制层接收网页请求并调用业务服务；业务服务层负责 AI 视觉调用和工单状态流转；数据访问层通过 JDBC 操作 SQLite。视觉模型通过独立的服务适配器接入，避免将特定服务商的请求格式耦合到控制器或网页代码中。

5.3 核心数据流程
用户上传图片，控制层检查文件是否为空及文件类型。
AI 服务适配器调用所选视觉模型，并将响应解析为统一的风险对象。
页面展示风险类别、风险等级、可见证据和整改建议，并标明需要人工确认的内容。
用户确认风险后，业务服务创建整改工单并保存到 SQLite。
责任人提交整改说明，工单状态变为 PENDING_REVIEW。
复查人员通过复查则状态变为 CLOSED；未通过则退回 PENDING_REMEDIATION。
5.4 工单状态设计
PENDING_REMEDIATION（待整改） → PENDING_REVIEW（待复查） → CLOSED（已关闭）
若复查未通过，状态由 PENDING_REVIEW 返回 PENDING_REMEDIATION。状态转换由后端服务校验，避免仅依赖前端控制。

七、风险控制与项目边界
AI 识别仅针对图像中可见的信息；不能仅凭图片断言设备正在通电、化学品具体成分或其他不可见事实。
模型输出不应自动触发高影响操作；创建工单前应进行人工确认。
视觉 API 调用失败、超时或返回格式不符合预期时，系统应提示失败并保留必要日志，不得伪造识别结果。
演示模式数据必须明确标记，不能用于声称模型已完成真实图片分析。
API 密钥通过环境变量或本地配置管理，不提交到 Git；测试图片应获得使用授权并避免泄露敏感信息。
八、总结
LabGuard AI 以 Java 作为主要开发语言，采用 Spring Boot、Thymeleaf、SQLite 和 Maven 构建轻量化原型。项目的重点是将视觉 AI 能力与人工确认、整改工单和复查闭环结合，形成可运行、可验证、可扩展的安全巡检工作流。真实 AI 能力的完成度取决于后续对所选视觉 API 的适配、测试和验证。
