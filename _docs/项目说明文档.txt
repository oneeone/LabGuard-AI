
实验室安全巡检智能体
项目说明文档
2026“仓颉杯”智能编程大赛｜创新原型赛道
核心理念：让实验室隐患从“被发现”走向“被整改、被复查、可追踪”。


一、项目背景
实验室是高校开展教学实验与科研活动的重要场所，通常包含实验设备、电气设施、实验器材及不同类型的实验材料。在日常使用过程中，通道被物品占用、设备或器材摆放不规范、电源使用不当、危险区域管理不到位等情况，可能带来安全隐患。传统巡检主要依赖人工现场检查和人工记录，检查效率与记录质量容易受到人员经验、巡检频率和工作负荷影响。
在实际管理中，发现问题并不等于完成管理闭环。如果巡检结果只停留在纸面记录或即时提醒，后续还可能出现责任人不明确、整改期限缺失、整改证据不足、复查过程不连续等问题。因此，实验室安全巡检需要的不仅是对现场照片进行描述的工具，还需要将疑似隐患识别、人工核验、整改任务和复查记录连接起来，形成可追踪的处理流程。
本项目拟开发“实验室安全巡检智能体”，将多模态视觉理解能力与轻量化业务流程相结合。系统通过分析用户上传的实验室照片，提取画面中可见的疑似隐患线索，并将分析结果转化为可确认、可分派、可复查的整改记录，帮助管理人员提高巡检记录的规范性与问题跟进效率。项目定位为辅助巡检原型，不替代专业安全人员的判断和学校现有安全管理制度。
二、应用场景
2.1 高校教学实验室日常巡检
实验课开始前或结束后，巡检人员拍摄实验室现场照片并上传系统。系统分析照片中可见的通道占用、物品摆放或其他预设类别的疑似问题，生成便于人工核验的巡检记录。确认存在问题后，可直接创建整改工单，减少重复填写和遗漏。
2.2 科研实验室定期检查
实验室管理员可按日、周或专项检查要求上传现场照片，对发现的疑似隐患进行统一记录。系统将原始照片、问题描述、整改责任人、截止日期和处理状态关联保存，便于后续查询和跟踪。
2.3 整改后的复查确认
责任人完成整改后，上传整改后的现场照片并提交说明。系统再次分析新照片，给出复查建议；授权巡检人员根据现场证据确认通过或退回整改。通过后关闭工单，未通过则保留原记录并退回处理，形成整改前后关联的证据链。
2.4 首版应用范围
考虑到创新原型赛道的开发周期和团队资源，首版重点验证“上传照片—识别疑似隐患—人工确认—生成工单—整改复查”的核心场景，优先选择一至两类能够从静态图像中观察的风险作为演示目标，例如消防通道或安全出口被物品遮挡、物品摆放影响通行等。对照片无法直接证明的事项，例如设备是否通电、设备内部状态或某种化学品的真实成分，系统应提示人工核验，不作确定性判断。
三、核心功能
3.1 巡检照片上传与记录
用户可上传 JPG、PNG 等常见格式的实验室现场照片，并填写实验室名称、巡检人员、巡检时间或补充备注。系统保存原始照片及其关联信息，创建一条巡检记录，为后续隐患分析和工单处理提供数据基础。
3.2 基于视觉模型的疑似隐患识别
系统调用具备图像理解能力的多模态模型，对照片中可见的风险线索进行分析。分析结果以结构化形式返回，建议包括：疑似隐患类别、画面位置描述、支持判断的可见证据、置信度或不确定性说明、建议整改措施，以及是否需要人工核验。模型负责提出线索和建议，不直接替代巡检人员作最终安全结论。
3.3 风险建议与人工确认
系统根据预设规则和隐患类别给出建议风险等级，并展示模型分析依据。巡检人员可确认、修改或驳回识别结果。对证据不足、图像模糊或模型输出异常的情况，系统应标记为“需人工核验”或提示重新上传，避免将不确定结论当作事实。
3.4 整改工单生成与跟踪
对人工确认的隐患，用户可创建整改工单。工单包含隐患描述、原始照片、建议整改措施、责任人、截止日期、当前状态及备注。系统提供工单列表和状态查询，帮助使用者了解哪些问题待整改、哪些问题待复查以及哪些问题已经关闭。
3.5 整改照片上传与复查
责任人完成整改后，可上传整改后的照片并填写说明。系统再次调用视觉模型，针对整改目标给出复查建议。巡检人员根据证据确认通过或不通过：通过则关闭工单，不通过则退回整改，并保留复查意见。
3.6 历史记录与状态追踪
系统保存巡检记录、模型输出、人工确认结果、工单信息、整改照片和复查结论。用户可查看历史记录，并按工单状态进行筛选。通过关联记录，能够追踪某条隐患从首次发现到整改完成的处理过程。
四、创新点
4.1 从“图片问答”升级为“可执行的业务闭环”
项目不以生成一段图片描述作为终点，而是把视觉模型输出接入实际软件流程。结构化隐患结果可经过人工确认后转化为整改工单，并继续流转至整改提交、复查和关闭，实现从隐患发现到处理结果留痕的闭环。
4.2 视觉模型与可配置规则协同
项目将“识别线索”和“风险等级建议”分开处理：视觉模型负责理解图像并提出疑似问题，规则模块根据隐患类别、人工确认和预设条件生成风险建议。这种设计使风险规则更易解释、测试和调整，也降低了完全依赖模型自由生成结论带来的不确定性。
4.3 人机协同与不确定性提示
系统保留人工确认、修改和驳回入口，并对图像证据不足、模型调用失败或结果格式异常等情况进行提示。模型分析结果、人工最终确认结果分别记录，既利用了 AI 的效率优势，也保留了安全管理中的人工审核环节。
4.4 整改前后证据链
系统将首次巡检照片、隐患描述、整改工单、整改后照片和复查结果进行关联，形成前后可对照的处理记录。相较于只生成隐患清单的工具，本项目更关注问题是否被处理以及处理结果是否经过复查。
4.5 面向快速落地的轻量化设计
针对创新原型阶段的时间和资源限制，项目采用轻量化架构，集中实现一条可运行的核心功能主线。模块边界清晰，后续可在验证核心闭环后扩展更多隐患类型、视频抽帧分析、统计报表或权限功能。
五、技术方案
5.1 总体技术路线
系统采用轻量化单体应用架构，以 Python 实现业务逻辑，使用 Streamlit 构建交互界面，使用 SQLite 保存结构化业务数据，通过多模态视觉模型 API 完成图片分析。照片文件存放在本地指定目录，数据库保存文件路径及关联信息。该方案可减少前后端分离、独立部署服务和数据库运维的工作量，适合短周期原型开发。

5.2 核心数据流
用户上传现场照片，系统保存图片并创建巡检记录。
系统将图片发送给视觉模型，要求模型按照约定的字段返回疑似隐患结果。
程序校验模型响应的 JSON 格式和必需字段；若解析失败或调用异常，则提示用户重试或人工核验。
业务规则模块依据隐患类别和预设规则给出风险等级建议，并将模型证据展示给用户。
用户确认或修改隐患后，系统保存最终确认结果；用户可创建整改工单并填写责任人和截止日期。
责任人上传整改照片，系统进行复查分析；巡检人员确认后，工单转为已关闭或退回整改。
系统保存每个阶段的记录和状态，供历史查询与演示验证。

5.4 工单状态设计
首版建议使用以下状态流转：待确认 → 待整改 → 待复查 → 已关闭。复查未通过时，由“待复查”退回“待整改”。状态变更由业务逻辑统一控制，避免出现未确认隐患直接关闭、未提交整改照片却进入复查等不合理情况。
5.5 模型输出与异常处理
建议模型输出使用固定 JSON 结构，例如包含 hazards 数组，每条隐患包括 category、evidence、location、confidence、suggested_action 和 needs_human_review 等字段。程序需校验响应结构、字段类型和必填项，不能直接信任未经校验的模型文本。模型调用失败、网络异常、输出无法解析或图片质量不足时，应返回明确提示，保留重试或人工处理入口，不得使用硬编码的虚构识别结果冒充真实 AI 输出。
5.6 安全、隐私与边界
API 密钥通过环境变量或本地配置文件读取，不写入公开代码仓库。
演示图片应来自团队自有或已获得使用授权的素材；涉及人员信息时应进行必要遮挡。
需在说明材料中披露所使用的第三方模型、API、开源组件及数据来源。
系统结果属于辅助判断；对于图像无法证明的设备运行状态、化学品真实成分等，不做确定性结论。
高风险或证据不足的情况必须由具备相应职责的人员复核，系统不自动控制实验设备或替代正式安全流程。
六、首版实施范围与可验证成果
为保证项目在有限周期内完成，首版围绕一条核心闭环实施，优先保证以下功能真实可用：
上传一张实验室照片并保存巡检记录。
调用真实视觉模型，返回结构化疑似隐患结果。
展示可见证据和不确定性，支持人工确认、修改或驳回。
基于确认结果创建整改工单，填写责任人与截止日期。
上传整改后照片并完成复查，支持通过关闭或不通过退回。
使用 SQLite 保存数据，程序重启后仍能查询历史记录。
提供源代码、依赖说明、运行步骤、核心测试记录和完整流程演示视频。
首版暂不将实时视频监控、多角色复杂权限、消息通知、模型训练和多智能体协作作为必做功能。如核心闭环提前完成，再考虑增加简单统计或 CSV 导出等扩展能力。
七、预期成果与应用价值
项目预期形成一个可以本地运行的实验室安全巡检智能体原型，能够展示真实图像分析、结构化隐患记录、人工确认、整改工单创建以及整改复查流程。通过将视觉模型能力嵌入业务流程，项目验证 AI 不仅能够解释图像，还能够辅助生成和跟踪后续管理任务。
在应用层面，系统有望减少巡检记录的重复录入工作，提高问题描述的规范性，帮助管理人员更清晰地掌握整改进度，并保留整改前后的相关证据。在技术层面，项目验证视觉模型、规则引擎、轻量数据库和交互界面协同工作的可行性，为后续扩展更多隐患类别、统计分析或视频抽帧提供基础。
上述价值属于项目设计目标和预期效果；实际准确率、效率提升幅度及长期使用效果，需要在后续测试和真实场景试用中进一步验证。
八、总结
“实验室安全巡检智能体”面向实验室日常巡检与隐患整改场景，采用视觉模型分析、规则建议、人工确认和工单状态管理相结合的方式，构建从隐患发现到整改复查的轻量化闭环。项目在创新原型阶段坚持范围可控、功能真实、结果可追踪和过程可复现，重点验证一条有实际智能能力、能够完整运行的核心业务流程，而不是追求功能数量或停留在静态展示。
